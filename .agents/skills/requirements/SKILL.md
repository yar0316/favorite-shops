# Requirements（要件定義）スキル

対話形式でシステムの要件を定義し、`docs/features/<機能名>/requirements.md` に要件定義書を作成します。
ユーザーの「要求（したいこと）」を入力とし、システムの「要件（何をするか）」を明確にします。

## ワークフロー

### 1. 機能名の確認

対象となる機能の名前を確認します。

```
notify_user で質問:
「どの機能の要件定義を行いますか？機能名を教えてください。」
```

### 2. 要求定義書（User Needs）の確認

指定された機能の要求定義書（`docs/features/<機能名>/user-needs.md`）が存在するか確認し、存在する場合は読み込んでコンテキストに追加します。

```
「docs/features/<機能名>/user-needs.md の内容を確認しました。これをベースに要件定義を進めます。」
```

### 3. 一問一答でヒアリング

以下の項目を**1つずつ**質問します。必ず `notify_user` ツールを使用し、1回の呼び出しにつき**1つの質問のみ**を投げかけてください。

| 順番 | 項目 | 質問例 |
|------|------|--------|
| 1 | 機能概要 | 「この機能はシステムとして具体的に何を実現するものですか？概要を教えてください。」 |
| 2 | 機能要件 | 「必要な機能のリスト（ユースケース）を教えてください。（例: ユーザー登録、ログイン、パスワードリセット）」 |
| 3 | 画面・UIイメージ | 「どのような画面が必要ですか？画面遷移や操作フローのイメージがあれば教えてください。」 |
| 4 | データ要件 | 「この機能で扱う主なデータ項目は何ですか？（例: ユーザー名、メールアドレス、パスワードなど）」 |
| 5 | 非機能要件 | 「パフォーマンス、セキュリティ、可用性などで特に考慮すべき要件はありますか？（任意）」 |
| 6 | 外部連携 | 「外部システムやAPIとの連携はありますか？（任意）」 |
| 7 | 受け入れ条件 | 「この機能が完了したと判断できる条件（Acceptance Criteria）は何ですか？」 |

### 4. 要件の確認と提案

全てのヒアリングが終わったら、以下を確認します：

```
notify_user で確認:
「ヒアリング内容を整理しました。
この内容で要件定義書を作成してよろしいですか？
修正や追加したい点はありますか？」
```

### 5. 要件定義書の生成

全ての回答が揃ったら、`assets/requirements-template.md` を参考に要件定義書を作成します。

#### 出力先
```
docs/features/<機能名>/requirements.md
```

機能名はケバブケース（例: `user-login`）に正規化してディレクトリ名として使用します。

### 6. インデックスの更新

`docs/features/index.md` が存在する場合は、作成した要件定義書へのリンクを追加します。

## 重要なルール

- **必ず一問一答**: 複数の質問を一度に投げかけないでください
- **`notify_user` を使用**: 質問には必ず `notify_user` ツールを使用してください
- **回答を待つ**: 各質問の後、ユーザーの回答を待ってから次の質問に進んでください
- **スキップ可能**: ユーザーが「スキップ」「なし」などと回答した場合は、その項目を「特になし」として記録し次へ進んでください

## テンプレート

要件定義書のテンプレートは `assets/requirements-template.md` を参照してください。
