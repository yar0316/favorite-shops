# User Needs（要求定義）スキル

ユーザーの要求を**一問一答形式**でヒアリングし、`docs/features/<機能名>/user-needs.md` に要求定義書を作成します。

## ワークフロー

### 1. 機能名の確認
まず、対象となる機能の名前を確認します。

```
notify_user で質問:
「どの機能についての要求を整理しますか？機能名を教えてください。」
```

### 2. 一問一答でヒアリング

以下の項目を**1つずつ**質問します。必ず `notify_user` ツールを使用し、1回の呼び出しにつき**1つの質問のみ**を投げかけてください。

| 順番 | 項目 | 質問例 |
|------|------|--------|
| 1 | 背景・課題 | 「この機能が必要になった背景や、現在抱えている課題を教えてください。」 |
| 2 | 実現したいこと | 「この機能で実現したいことは何ですか？」 |
| 3 | 対象ユーザー | 「この機能を使うのは誰ですか？（例: 管理者、一般ユーザーなど）」 |
| 4 | ユーザーストーリー | 「具体的に、いつ・どこで・どのようにこの機能を使いますか？業務フローの中での位置づけも教えてください。」 |
| 5 | 期待する効果 | 「この機能によってどのような効果や価値が得られることを期待していますか？」 |
| 6 | 制約・条件 | 「実装にあたって考慮すべき制約や条件はありますか？（任意）」 |

### 3. 要求の確認と提案

全てのヒアリングが終わったら、以下を確認します：

```
notify_user で確認:
「ヒアリング内容を整理しました。
そのまま要求として記録しますか？
それとも、システムに合わせて調整・提案した方がよい点はありますか？」
```

ユーザーの回答に応じて：
- **そのまま記録**: 回答通りに要求定義書を作成
- **提案を求められた場合**: システム設計の観点から改善案を提示し、合意を得てから記録

### 4. 要求定義書の生成

全ての回答が揃ったら、`assets/user-needs-template.md` を参考に要求定義書を作成します。

#### 出力先
```
docs/features/<機能名>/user-needs.md
```

機能名はケバブケース（例: `user-login`）に正規化してディレクトリ名として使用します。

### 5. インデックスの更新

`docs/features/index.md` が存在する場合は、新しい機能へのリンクを追加します。存在しない場合は新規作成します。

## 重要なルール

- **必ず一問一答**: 複数の質問を一度に投げかけないでください
- **`notify_user` を使用**: 質問には必ず `notify_user` ツールを使用してください
- **回答を待つ**: 各質問の後、ユーザーの回答を待ってから次の質問に進んでください
- **スキップ可能**: ユーザーが「スキップ」「なし」などと回答した場合は、その項目を「特になし」として記録し次へ進んでください

## テンプレート

要求定義書のテンプレートは `assets/user-needs-template.md` を参照してください。
