# バックエンドテスト定義（backend-test）スキル

AWS Lambda + DynamoDB のバックエンド機能を実装する**前**に、振る舞い（Behavior）を定義する Small テストを作成するためのスキルです。
このスキルで作成されたテストコードが、そのまま詳細設計書および受け入れ条件として機能します。

## 前提条件

テスト作成を開始する前に、必ず以下のドキュメントを確認してください。
- `docs/features/favorite-shops/architecture.md`
- `docs/features/favorite-shops/database-design.md`

## ワークフロー

### 1. 対象ドメインと要件の確認

ユーザーにどの機能（ドメイン）のテストを作成するか確認します。
すでに機能要件（`requirements.md`等）が存在する場合はそれを読み込み、APIのインターフェース設計（入力と期待される出力）のイメージを共有します。

### 2. テストファイルの作成

`tests/functions/<domain>/` 配下に `test_handler.py` などの pytest ファイルを作成します。
**ここでは実際の Lambda 実装（`functions/<domain>/handler.py` 等）は作成しません。** あくまでテスト側だけを先行して記述します。

### 3. テスト記述の基本ルール

1. **ユースケースの網羅**
   - 正常系だけでなく、想定される異常系（バリデーションエラー、認証エラー、DBエラー、対象アイテム不在等）のテストケースを列挙してください。
2. **外部依存のモック**
   - AWSの各種API呼び出し（DynamoDBなど）は `stubber`（boto3）等を用いて必ずモック化する前提でテストを記述します。
   - 外部との結合は行わない「Smallテスト」として完結させてください。
3. **Pydanticモデルの想定**
   - データの入出力仕様を明確にするため、「このような Request/Response モデルが存在する想定」でテストコード内に型宣言・インポート文を記述してください。（実際の `models.py` がまだ無くても構いません）

### 4. ユーザーレビューの実施

テストコード（＝詳細設計）が書き上がったら、ユーザーに以下の点でレビューを依頼します。
- 「これらのユースケース（テストケース）で要件を満たしているか？」
- 「APIのリクエスト/レスポンス構造（モデル）はこれで問題ないか？」

### 5. 次のステップの提示

ユーザーからテスト仕様（詳細設計）の承認を得たら、実際のバックエンド機能実装に進むため、「実装には **backend-dev** スキルをご利用ください」とナビゲートして完了します。
